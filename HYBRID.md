# HYBRID.md — переход на Polar.sh + гибридная монетизация

Рабочий план. Фазы `[ТЫ]` требуют ручных действий (аккаунты, деньги, решения), фазы
`[АГЕНТ]` отдаются ИИ-агенту одной задачей. У каждой агентской фазы есть критерий
готовности — без него фазу не закрывать.

**Контекст кода на момент написания плана:** биллинг-поверхность маленькая —
`backend/app/services/billing.py` (188 строк), `backend/app/api/billing.py` (24),
`backend/app/api/webhooks.py` (55), миграция `006_billing.sql`,
`frontend/src/app/(app)/billing/page.tsx` (394). В `payments` **уже есть колонка
`provider`** — схема с самого начала допускает двух провайдеров одновременно.

## Критический путь

- Фазы 0→1→2→3→4→5 — приём денег. Делать целиком и подряд.
- Фаза 6 — удаление CloudPayments, отложена по календарю (когда истечёт последняя CP-подписка).
- Фазы 7→9 — капча/прокси в облаке, то, за что реально платят. Можно вести параллельно
  с фазой 5, по файлам не конфликтуют.
- Фаза 10 — двадцать минут работы и заметная маржа. Забирать первой из гибрида.

# Фаза 0 [ТЫ] — проверить, что Polar вообще применим

**Не начинать кодить, пока не отвечены три вопроса.** Polar — merchant of record поверх
Stripe. Отсюда два риска, оба фатальные для продукта под hh.ru/hh.kz:

1. **Выплаты в Казахстан.** Polar выплачивает через Stripe Connect, список стран у Stripe
   ограничен, и KZ в нём скорее всего нет. Проверить раздел про payouts / supported
   countries в их доках **и спросить напрямую в их Discord** — ответ из первых рук
   надёжнее доков.
2. **Приём российских карт.** Мир и карты подсанкционных банков на Stripe не проходят
   вообще. Посмотреть в дашборде CloudPayments долю платежей RU-картами. Если она
   значимая — переход на Polar её обнулит.
3. **Экономика.** Polar ≈ 4% + $0.40 с транзакции, но как MoR берёт на себя НДС и
   отчётность. CloudPayments дешевле по проценту, но налоговый агент — ты. При чеке
   ~1990 ₽ фикс в $0.40 весит ощутимо — посчитать на своём среднем чеке.

**Развилка:**

| Результат проверки | Что делать |
|---|---|
| Всё три ОК | Идти по плану, CloudPayments в итоге удалить (фаза 6) |
| Выплаты в KZ есть, но RU-карты важны | **Оставить оба провайдера.** `payments.provider` уже готов: Polar для KZ/международных, CP для RU. Фаза 6 выпадает, остальное без изменений |
| Выплат в KZ нет | Polar отпадает. Смотреть Paddle (тоже MoR, свой список стран) или остаться на CP и вложить силы в часть II — она даёт больше денег, чем смена провайдера |

Дальше план написан в предположении, что Polar подходит.

# Часть I. CloudPayments → Polar

## Фаза 1 [АГЕНТ] — Polar в бэкенде, рядом с CP, а не вместо

Ключевое решение: **никакого абстрактного `BillingProvider` с двумя реализациями.**
Один env-флаг, функции рядом в том же файле. Интерфейс на два провайдера, один из
которых скоро удалят, — это ровно та сложность, которую потом кто-то расшифровывает
в 3 утра.

Задание:

- `config.py`: `PAYMENT_PROVIDER: str = "cloudpayments"`, `POLAR_ACCESS_TOKEN`,
  `POLAR_WEBHOOK_SECRET`, `POLAR_SERVER: str = "sandbox"`. В `PLANS` — поле
  `polar_product_id` рядом с `price`.
- Миграция `024_polar.sql`: `profiles.polar_customer_id`, `profiles.polar_subscription_id`.
  `payments` не трогать — `provider='polar'`, `provider_payment_id` = Polar order id,
  идемпотентность работает как есть. Применяется сама на следующем `docker compose up`
  (сервис `migrate`), проверить `docker compose logs migrate`.
- `services/billing.py`: `polar_checkout_url(user_id, plan_id)` → Checkout Session с
  `external_customer_id = user_id` (замена костыля `AccountId`) и `success_url`;
  `verify_polar_webhook(raw, headers)`; `process_polar_event(event)`.
- `api/webhooks.py`: эндпоинт `/api/webhooks/polar`, тот же паттерн — 200 при валидной
  подписи всегда, `run_in_executor`, никогда не 500.
- События: `order.paid` (запись платежа), `subscription.active` / `subscription.canceled`
  / `subscription.revoked` (состояние плана).
- `api/billing.py`: `/subscribe` возвращает `{"checkout_url": ...}` при провайдере polar,
  старый `SubscribeResponse` при cloudpayments.

**Что удаляется:** `_plan_for_amount` и `_period_end`. Polar присылает
`current_period_end` в подписке — брать срок от провайдера честнее, чем угадывать план
по сумме платежа. Заодно исчезает баг «два плана с одинаковой ценой не различить».

**Обязательно:** сверить формат вебхуков и параметры Checkout API по живой документации
Polar (context7 / WebFetch на docs.polar.sh), а не по памяти модели. Polar активно
меняется. Подпись вебхука — по стандарту Standard Webhooks; в их Python SDK есть готовый
валидатор, использовать его, а не писать HMAC руками.

**Готово когда:** `cd backend && python -m pytest tests/test_billing.py -v` зелёный,
включая новые тесты: валидная подпись → план активирован, битая → 403, дубль
`order.paid` → активация не повторилась. Старые CP-тесты не тронуты и тоже зелёные.
CI (`.github/workflows/ci.yml`) зелёный.

## Фаза 2 [ТЫ] — настроить Polar sandbox

1. Аккаунт на `sandbox.polar.sh`, организация.
2. Создать продукты по числу планов из `config.py` (Спринт, Месяц) с recurring-интервалами.
   **Скопировать product ID** → в `polar_product_id`.
3. Webhook endpoint в дашборде. Нужен публичный URL → `ngrok http 8000` или Cloudflare
   Tunnel. Подписаться на `order.paid`, `subscription.active`, `subscription.canceled`,
   `subscription.revoked`.
4. В корневой `.env`: токен, webhook secret, `PAYMENT_PROVIDER=polar`, `POLAR_SERVER=sandbox`.
5. `docker compose build api && docker compose up -d api` — код в контейнере запечён, без
   ребилда правки не подхватятся.

## Фаза 3 [АГЕНТ] — фронтенд

- Выкинуть из `billing/page.tsx` загрузчик скрипта CP и объект виджета (~60 строк в минус).
- `subscribe(planId)` → `apiFetch` → `window.location.href = checkout_url`. Всё.
- Страница `/billing/success` — «оплата прошла, план активируется в течение минуты» +
  поллинг `/api/billing/status`. Вебхук может прийти на секунду позже редиректа, не
  показывать пользователю «не оплачено».
- Кнопка «Отменить подписку» → редирект в **Customer Portal** Polar. Это убирает
  `billing.cancel` с его комментарием «реальная отмена вручную через поддержку» — то есть
  закрывает существующий долг, а не добавляет новый.

**Готово когда:** `cd frontend && npx tsc --noEmit && npm run build` без ошибок, в коде
фронта нет строки `cloudpayments.ru`.

## Фаза 4 [ТЫ] — e2e в sandbox

Тестовой картой Polar пройти: подписка → `profiles.plan = 'active'` → доступ к воркеру
появился → отмена в портале → `plan='cancelled'`, но доступ жив до `plan_expires_at`.
Отдельно: отправить тот же вебхук дважды (кнопка redeliver в дашборде) → в `payments`
одна строка.

## Фаза 5 [ТЫ] — прод и существующие подписчики

**Токены рекуррентных списаний CloudPayments в Polar не переносятся** — технически
невозможно, это карточные токены на стороне CP. Значит:

1. Продовая организация Polar, продовые продукты, продовый webhook URL (уже не ngrok),
   `POLAR_SERVER=production`.
2. **CloudPayments не выключать.** Действующие подписки доживают оплаченный период на CP.
3. Новые оплаты идут в Polar (`PAYMENT_PROVIDER=polar`).
4. Письмо + баннер в UI действующим платящим: «переоформи подписку до <дата>». Ждать, что
   переоформятся все, не стоит — заложить отвал.

## Фаза 6 [АГЕНТ] — удалить CloudPayments

Только когда
`select count(*) from payments where provider='cloudpayments' and expires_at > now()`
вернёт 0.

Удаляется: `verify_hmac`, `subscribe_params`, `process_payment`, `_parse_amount`, эндпоинт
CP-вебхука, CP-настройки из `config.py` и `.env.example`, CP-тесты, флаг
`PAYMENT_PROVIDER` (провайдер один — флаг больше не нужен). Колонку
`profiles.cp_subscription_id` оставить: ничего не стоит, а история платежей по ней читается.

Обновить `CLAUDE.md`, `README.md`, `docs/my_docs/DEPLOY.md` — CloudPayments упоминается
во всех трёх.

# Часть II. Гибридная монетизация

Принцип границы: публично **всё, что описывает логику**; приватно **только то, что нельзя
воспроизвести без твоих ресурсов** — твои деньги (OpenAI), твоя инфраструктура (прокси,
IP-репутация), твои накопленные данные.

Тест на границу: «если конкурент прочитает этот файл, он получит преимущество?» Промпт —
нет, воспроизводится за день. Пул живых прокси, которые hh ещё не забанил — да, и его не
скопируешь чтением.

Механизм уже есть в коде: пустой `OPENAI_API_KEY` → шаблоны, капча → `captcha_requests` и
человек, нет веб-сессии → легаси API. Это ровно структура «premium выключен → работает
базово». Гибрид = подключить платный путь в те же точки ветвления, **не добавляя новых
слоёв абстракции**.

## Фаза 7 [ТЫ] — граница и ресурсы

1. Приватный репозиторий `otclick-cloud`, поддомен под него.
2. Капча-провайдер (2captcha, CapSolver — что дешевле на объёмах), пополнить баланс.
3. Резидентские прокси KZ/RU. Самая дорогая строка расходов — начать с минимального
   пакета и мерить, сколько откликов на один IP hh терпит.
4. **Записать границу словами, до кода.** Публично: логика откликов, фильтры, воркер,
   промпты, аналитика по своим данным. Приватно: решение капчи, пул прокси, ключ OpenAI,
   кросс-юзерные агрегаты. Спорное — по умолчанию публично.

## Фаза 8 [АГЕНТ] — приватный сервис

Отдельный репозиторий, минимальный FastAPI:

- `POST /captcha/solve` — картинка → решение, проксирует в капча-провайдера
- `GET /proxy/lease` — выдать прокси-URL из пула
- Аутентификация: один статический bearer-токен на инстанс. OAuth не нужен, клиент ровно
  один — твой воркер.

**Готово когда:** оба эндпоинта отвечают локально, один smoke-тест на каждый.

## Фаза 9 [АГЕНТ] — тонкий клиент в публичном коде

- `config.py`: `OTCLICK_CLOUD_URL: str = ""`, `OTCLICK_CLOUD_TOKEN: str = ""`.
- `services/captcha.py`: если URL задан — попытка автосолва; при любой ошибке или пустом
  URL — существующий путь через `captcha_requests` и человека. Fallback не переписывать,
  он уже работает.
- `hh/client.py`: если URL задан — исходящие запросы через арендованный прокси, иначе
  напрямую. Точка одна — `BaseClient`, не править каждый вызов.

**Готово когда** (самая важная проверка всего плана): полный сценарий отклика проходит с
пустым `OTCLICK_CLOUD_URL`, и этот тест добавлен в `.github/workflows/ci.yml`. Пока он
зелёный — self-host честно рабочий, а не сломанная демка. В день, когда он покраснеет, ты
перестал быть open source по факту, что бы ни было написано в README.

## Фаза 10 [ТЫ] — AI без кода

`OPENAI_BASE_URL` уже в конфиге. Поставить свой gateway (или прямо ключ) в проде — ноль
правок кода. Self-host приносит свой ключ, у тебя ключ включён в подписку. Ровно то, за
что берутся деньги, и ровно нуль строк.

## Фаза 11 [АГЕНТ] — лимиты по плану

`worker/limiter.py` уже считает дневные/часовые капы на юзера. Привязать значения капов к
`profiles.plan` вместо глобальных настроек. Спринт — меньше, Месяц — больше.

Сверх-лимиты пакетами (у Polar есть usage-based billing на метриках) — **только когда
упрёшься в реальный спрос**, не заранее.

## Фаза 12 [ТЫ] — позиционирование

README: явная таблица «self-host vs хостинг» — что даёт облако, что работает без него.
Врать про self-host нельзя, обнаружат за час и напишут об этом там, где ты не увидишь.
Честная таблица работает лучше маркетинга: человек сам поймёт, что капчу ночью решать не
хочет.

## Главная ловушка

Не кормить приватным сервисом то, что нужно для базовой работоспособности. Если публичная
версия без облака не может **отправить отклик** — это не open source, а сломанная демка, и
траст (единственная причина держать код открытым, когда просишь доступ к hh-аккаунту)
обнуляется. Критерий из фазы 9 существует именно для этого.
